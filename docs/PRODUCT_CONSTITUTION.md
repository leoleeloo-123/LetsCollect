# Let's Collect 产品宪法

状态：草案 v1  
日期：2026-07-13  
用途：在继续开发界面和功能前，统一产品方向、体验原则与工程边界

## 一、产品定义

Let's Collect 是一个以 3D 数字收藏玩具为核心、优先服务手机端的收藏产品。

社交互动是参与的起点，抽取券是连接互动与收藏的媒介，抽取是情绪高潮，收藏则是用户长期留下来的原因。

产品的核心循环是：

```text
互动 -> 获得抽取券 -> 抽取 -> 收藏 -> 分享 -> 再次互动
```

Let's Collect 不是单纯的 3D 模型展厅，不是传统社交网络，也不是通用抽卡界面。所有重要功能都应至少强化核心循环中的一个环节；无法说明价值的功能，不进入首期版本。

## 二、产品原则

1. 收藏玩具始终是视觉与情感中心。
2. 手机端是默认体验，桌面端只做增强。
3. 一个页面只承担一个主要任务，并保留一个最明确的主操作。
4. 3D 只在用户聚焦某只玩具时出现，不作为列表装饰到处加载。
5. 社交功能以轻量互动创造价值，不追求复杂的内容网络。
6. 稀有度和所有权应该有情绪价值，但不能依赖过量视觉特效。
7. 先用 Mock 数据验证产品结构，再引入认证、数据库和真实业务规则。

## 三、一级导航

首期产品固定为四个手机端一级入口：

| 模块 | 用户进入时的问题 | 主要结果 |
| --- | --- | --- |
| 首页 | 今天发生了什么，我怎样获得抽取券？ | 与好友动态互动，或进入本期抽取 |
| 抽取 | 现在可以抽什么？ | 消耗抽取券并揭晓一只收藏玩具 |
| 收藏 | 我拥有什么，还缺少什么？ | 查看系列进度并检查选中的玩具 |
| 好友 | 我正在和谁一起收藏？ | 管理好友关系并了解朋友的收藏状态 |

`Explore` 不作为首期一级入口。发现能力分别存在于首页动态、本期抽取、系列入口和收藏页中。

`Profile` 不作为首期一级入口。账户与设置从头像等二级入口进入。

## 四、模块职责

### 首页

首页是发现与好友动态流，不是营销落地页。

首页应包含：

- 当前抽取券与简洁账户入口；
- 本期抽取池或当前系列入口；
- 好友获得新藏品和系列进度动态；
- 可以获得抽取券的轻量互动任务；
- 必要时出现的小型活动、挑战或排行入口。

首页最重要的行为，是通过有意义的好友互动推进下一次抽取。

### 抽取

抽取页是最有仪式感、信息密度最低的一级模块。

抽取页应包含：

- 当前抽取券和单次消耗；
- 一个明确选中的抽取池；
- 本期核心玩具或系列视觉；
- 单次抽取，以及未来可能出现的多次抽取；
- 不干扰主操作的概率与规则入口；
- 聚焦的揭晓结果，以及前往收藏或分享的路径。

抽取概率逻辑与揭晓动画必须分离。未来真实抽取结果必须由服务端产生。

### 收藏

收藏是产品的情感中心。

收藏页应包含：

- 已拥有玩具与未解锁剪影；
- 系列进度和稀有度信息；
- 使用轻量缩略图的浏览体验；
- 选中玩具后的详情浮层或底部抽屉；
- 只为当前选中玩具加载的 3D 检查体验。

收藏页默认展示收藏网格，而不是同时运行多个 WebGL 画布。

### 好友

好友模块负责关系管理，不发展成完整社交网络。

好友页应包含：

- 好友列表；
- 好友申请、邀请和添加流程；
- 好友收藏概览；
- 必要时出现的轻量排行或比较；
- 返回首页互动场景的路径。

复杂聊天、公开关注体系和独立社交内容平台不属于首期范围。

## 五、3D 资产策略

3D 模型是产品的核心资产，必须作为可复用能力管理。

- 列表和动态流使用优化过的 AVIF、WebP 缩略图或海报图；
- 只有主视觉、玩具详情、抽取揭晓或用户明确进入检查状态时才加载 GLB；
- 模型路径保存在玩具数据或资产配置中，不散落在页面组件里；
- 大型 GLB 作为公开静态资源部署，不导入 JavaScript Bundle；
- 手机端和桌面端可以使用不同精度、不同 URL 的模型；
- 可复用的 `ToyViewer` 统一管理加载、居中、相机、灯光、控制、状态、清理和性能档位；
- 文本、按钮、导航和卡片继续使用标准 React DOM，不放入 3D Canvas。

当前独立 Hero HTML 是经过验证的视觉和技术参考，但不是未来产品页面架构。迁移时只迁移其中已经验证的能力，不整体复制旧页面。

## 六、视觉方向

产品界面应当高级、克制、有触感，并让人产生收藏欲。

- 玩具拥有页面中最高的视觉优先级；
- 一个屏幕只保留一个主要视觉焦点；
- 发光、玻璃、粒子和稀有度效果应选择性使用；
- 避免仪表盘式密度、装饰性卡片堆叠和通用营销页构图；
- 重复藏品可以使用卡片，页面大区块保持开放和清晰；
- 触控尺寸、字号、导航、加载策略和手势首先围绕手机设计；
- 桌面端可以显示更多上下文，但不能改变任务层级。

## 七、核心数据对象

首期领域模型围绕以下对象组织：

- `User`：用户；
- `Toy`：玩具；
- `Series`：系列；
- `Rarity`：稀有度；
- `CollectionItem`：用户拥有的收藏项；
- `SocialPost`：好友动态；
- `Interaction`：互动记录；
- `Friendship`：好友关系；
- `TicketTransaction`：抽取券流水；
- `DrawPool`：抽取池；
- `DrawResult`：抽取结果。

玩具资产引用应集中管理，例如：

```ts
toy.assets.thumbnailUrl
toy.assets.posterUrl
toy.assets.modelUrl
toy.assets.mobileModelUrl
```

Mock 数据也必须遵守这些边界，以便未来接入 Supabase 时替换数据来源，而不重写页面。

## 八、首期明确不做

- 复杂私信、群聊或实时聊天；
- 公开创作者网络或通用社交信息流；
- 视频优先内容；
- 市场交易、转售、支付或区块链所有权；
- 完整后台管理系统；
- 任何真钱抽取机制；
- 为每个列表项加载 GLB；
- 超过四个一级导航入口；
- 在 Mock 流程验证前接入真实认证、真实概率或数据库写入。

## 九、实施阶段

### 阶段 0：锁定方向

- 审阅并确认本产品宪法；
- 对齐产品概览、架构、路由和路线图；
- 判断当前 React 分支中哪些骨架继续保留。

### 阶段 1：信息架构 MVP

- 完成四模块手机端骨架和 Mock 内容；
- 验证导航、页面层级和主操作；
- 提供加载、空状态和错误状态；
- 3D 暂时使用明确占位边界。

### 阶段 2：核心互动闭环

- 验证互动获得抽取券；
- 验证消耗抽取券；
- 验证抽取揭晓和收藏更新；
- 所有行为先在本地以可测试的 Mock 状态运行。

### 阶段 3：视觉系统

- 统一字体、颜色、间距、稀有度、动效和触控反馈；
- 验证手机性能与可访问性；
- 视觉收敛阶段不增加新的产品功能。

### 阶段 4：可复用 3D 查看器

- 建立独立 `ToyViewer` 边界；
- 从 Legacy 原型迁移已经验证的 GLB 加载和检查能力；
- 分别验证首页主视觉、详情和揭晓场景。

### 阶段 5：后端接入

- 接入 Supabase Auth 与行级安全策略；
- 接入收藏、好友、互动、抽取券流水、抽取池和结果；
- 所有权、抽取券和抽取结果由服务端可靠写入。

## 十、阶段验收闸门

进入下一阶段前，当前阶段必须回答自己的核心问题：

| 阶段 | 必须回答的问题 |
| --- | --- |
| 产品方向 | 四个模块是否共同服务同一个核心循环？ |
| 信息架构 | 手机用户能否在没有说明的情况下知道下一步去哪里？ |
| 互动闭环 | 用户能否用 Mock 数据完成“互动 -> 获券 -> 抽取 -> 收藏”？ |
| 视觉系统 | 产品能否在不过度依赖特效的情况下呈现收藏价值？ |
| 3D 查看器 | 同一个查看器能否在手机端稳定服务主视觉、详情和揭晓？ |
| 后端 | 所有权、抽取券、好友关系和抽取结果是否安全且具有权威来源？ |

## 十一、变更规则

本文件是决策基线，不是永远不能修改的规格书。

如果要改变一级导航、核心循环、3D 加载策略或首期非目标，应先更新本文件，再进入实现。小型视觉和文案调整不需要修改宪法。

任何新增大型功能都应说明：它强化了核心循环的哪一环，以及它带来了什么复杂度。

## 十二、当前 MVP 说明

当前 React MVP 用浏览器本地状态验证以下流程：

```text
好友动态互动 -> 增加抽取券 -> 消耗抽取券 -> Mock 揭晓 -> 收藏数量更新
```

它不是正式抽取系统，也不代表未来概率、票券经济或好友规则。当前数据可以在好友页重置，并会保存在本机浏览器中，便于持续体验和调整。
